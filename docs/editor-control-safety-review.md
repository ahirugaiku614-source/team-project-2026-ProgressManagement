# PR #9 マージ前の追加確認

## 1. FastAPIの依存関係と所属削除

エディタのHTTP経路は次の順で解決する。

1. Security(HTTPBearer)から取り出した値をverify_editor_firebase_tokenで検証する。
2. Firebase SDKへcheck_revoked=Trueを渡す。Cookie・クエリの値は使わない。
3. editor_memberが既存get_project_team_memberを呼び、UID→User→現在のTeamMemberを確認する。
4. editor_projectが既存get_accessible_projectを呼び、Project.team_idとの対応を確認する。
5. bindingが同じ認証済みUser/Projectから所有関係を作る。

同じリクエスト内では、projectとbindingが使うeditor_memberがFastAPIのDependsキャッシュを
共有するため、Firebase検証を重複して実行しない。リクエストをまたいだ認可キャッシュはない。
既存の同一セッション内削除テストに加え、別DB接続でTeamMemberの削除をコミットした直後に、
同じトークン・同じHTTPクライアントのGET/start/stop/sessionsがすべて403になることを検証する。
残る正規メンバーの要求は200であり、チーム全体を誤って失効させない。

削除確定前に認可が済んだ要求まで取り消す保証はない。現在の操作は全て実行無効なので、
その場合も起動・停止・接続セッション発行は起こらない。
将来の実行・継続WSではワーカー直前の再認可、短期許可、接続中の失効が別途必要。
現在のWebSocketは誰であってもacceptせず1008で閉じる。

## 2. Docker作成途中の失敗と残存物の特定

### 見つかった問題

従来の診断試験はdocker create/volume createの成功応答の後にだけリソースをメモリへ登録した。
デーモン側で作成済みでもCLI応答が失われると一覧に載らず、誤削除はしないものの、
失敗後に残存物の正確な名前を調べる根拠が弱かった。

### 修正後の順序

tools/editor_lab_resources.pyに、診断専用の記録・照合をまとめた。
これはアプリAPIや実エディタのワーカーではなく、ホストから明示実行するテスト補助である。

1. ローカルの新規一時ディレクトリに実行IDとジャーナルJSONを作り、場所を表示する。
2. DockerのデーモンIDを記録する。接続URL・資格情報・ホストマウントパスは保存しない。
3. UUIDから生成した正確な名前をPLANNEDとして、作成コマンドを呼ぶ前に保存する。
4. 同名不存在、デーモン一致を確認して作成する。
5. inspectの名前・所有ラベル・コンテナ不変ID/ボリューム作成時刻と応答を照合しCONFIRMEDへ進める。
6. timeout、作成失敗、inspect不能、既存名、応答不一致はUNCERTAINとして保全する。
   例外には実行ID・ジャーナル場所だけを付け、生のDockerエラーや設定は出さない。

一件でも結果不明・所有権不一致・デーモン変更・実行中があれば、自動の後片付け全体を止める。
そのコンテナが使っているかもしれない確認済みボリュームも勝手に消さない。
全件照合できる正常系だけで、コンテナを不変IDで先に削除し、確認済みボリュームを後に片付ける。
force、stop、pruneは使用しない。削除応答を失った場合も、その後の削除へ進まず記録を残す。
既存のcode_server_workspace等は名前もラベルも対象に含まれない。

### 読み取り専用の復旧確認

テスト開始時・例外に表示されるジャーナルは成功後も残し、REMOVEDも記録する。
再実行は別UUIDとなり、前のUNCERTAINを採用・削除しない。
失敗したジャーナルを一時ファイル掃除等で失わないよう、管理者が保全する。

```powershell
python tools/editor_lab_resources.py --report <ジャーナルJSONのパス>
```

このCLIはinfoと記録された正確な名前のinspectだけを実行し、削除を行わない。
Dockerが停止中でもローカルの計画名を列挙してcontext_unavailableと報告する。
別デーモンならcontext_mismatchでinspectを行わない。
不存在と接続障害を区別できない場合はnot_found_or_unavailableとし、残存なしと断定しない。
所有ラベル一致・ID差替え・不一致も区別するが、一致したから自動削除してよいとはしない。

管理者は実行IDとデーモンを確認し、記録・対象設定・実マウント・停止状態を保全してから
残存物を個別に判断する。CLIに削除オプションはなく、汎用の削除・prune手順も提供しない。
Dockerを無理に再起動したり、既存アプリのコンテナやボリュームを止めたりしない。

### 保証の限界

Docker API自体にはボリューム削除のcompare-and-swapがなく、不変IDもない。
名前・ラベル・作成時刻・デーモンを照合しても、ホスト管理者が直前に同名を差し替える
敵対的な競合まで保証しない。試験中の同時リソース変更を避け、結果不明時は保全する。
コンテナは名前ではなく不変IDで削除するため、同名差替えで別コンテナを消さない。
ジャーナルはファイルfsyncと原子的置換、POSIXでは親fsyncを行うが、実電源断・OS/媒体故障は未検証。

## 3. 既存Firebaseエラー露出と互換性

従来のverify_firebase_tokenは、SDK例外のstr(error)をdetailへ付けて返していた。
例外にトークン、内部パス、接続先等が含まれた場合、既存APIのHTTP応答へ露出し得る。
PR #9の新しいエディタ依存関数は独立して例外を固定401へ変換しているので、
既存の所属解決関数を再利用してもこの生エラーは経由しない。

追加修正では既存API側もHTTPのdetailを以下へ固定した。

```json
{"detail":"Invalid or expired authentication token"}
```

既存のverify_id_token呼出し引数、正常時のclaims、401、WWW-Authenticate: Bearerは変更しない。
既存API全体へcheck_revokedを追加する変更はせず、エディタだけTrueを維持する。
既存クライアントがSDKの生のエラー文へ依存していた場合は本文が変わるが、
その詳細は公開APIの仕様とせず、認証エラーはHTTPステータスで扱う。
startup時の資格情報ロードや既存API全体の認証方式の刷新は今回の対象外。

/api/me、/api/teams、Project一覧で内部文字列入りのSDK例外を注入し、固定401・ヘッダー・
検証モードを確認する。正常な既存APIとエディタAPIも成功することを確認する。
実Firebase通信を使った失効・障害試験は未実施で、SDKの呼出し境界だけを代替している。

## 4. 回帰検証と既存データ保護

所属削除、依存の要求単位キャッシュ、既存認証の非露出を追加確認する。
Docker障害は模擬デーモンで作成前失敗・作成応答消失・inspect障害・既存名衝突・
所有権変更・同名再作成・デーモン変更/停止・実行中・削除応答消失を注入し、
既存リソースへ削除が発行されないこと、読み取り専用で計画名を特定できることを確認する。
正常系の実診断コンテナも、今回作ったUUID名・所有ラベル付きの一時領域だけで再実行する。
稼働中のDocker設定・コンテナ、PostgreSQL、共有Git、workspace、既存ボリュームは変更しない。
実行ゲートは常時無効のままで、mainへのマージや稼働ソースへの配備は行わない。
