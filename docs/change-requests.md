# 第3段階：コード変更の提出・レビュー依頼API

## できることと今回の範囲

mainの`c1c262e`から`feat/change-request-api`を作成しました。
認証済みのチームメンバーが自分の個人作業領域を提出し、同じプロジェクトのチームメンバーが
一覧・詳細・変更ファイル・差分を取得できます。GitやGitHubの利用者アカウントは不要です。

承認、差し戻し、状態変更、共有mainへの統合、最新版取得、Vue画面、個人code-serverの本番起動は追加しません。
このAPIは既存の共有bareリポジトリと個人作業領域を使います。
DB・Git・ファイル・Dockerボリュームの削除／初期化し直しは行いません。

## データモデル

`ChangeRequest`を`change_requests`テーブルへ追加しました。

| 項目 | 内容 |
| --- | --- |
| id | レビュー依頼番号 |
| project_id | Projectへの外部キー。Projectからchange_requestsを参照可能 |
| submitted_by | 提出者Userへの外部キー。認証済みユーザーから設定 |
| request_key | クライアントが発行するUUID形式の提出キー。同じ提出の再試行に使用 |
| title / description | タイトル1〜200文字、説明は省略可・最大10,000文字 |
| state | OPEN / CLOSED。今回はOPENの作成のみ |
| snapshot_commit | 提出ファイルを固定したSHA-1コミットID |
| base_commit | 提出時点で読み取った共有mainのコミットID |
| git_ref | refs/change-requests/サーバー生成キー/head |
| created_at / updated_at | UTCの作成日時・更新日時 |

外部キーはRESTRICTで、関連データの連鎖削除はありません。
状態・文字数・コミットID長のCHECK制約、Git参照と(Project, User, request_key)の一意制約、
プロジェクト別一覧用のインデックスを追加しました。IDの16進形式はGit操作前にも検証します。
DB管理者による直接書き換えまで防止するものではなく、APIにはコミットIDの変更機能を設けていません。

## 利用手順とAPI

既存の`GET /api/me`でユーザーを同期し、チーム所属とProject作成を済ませてください。
既存の`POST /api/teams/{team_id}/projects/{project_id}/workspace/init`で個人領域を初期化します。
提出・差分APIが領域を勝手に作り直すことはありません。

共通パスは`/api/teams/{team_id}/projects/{project_id}/change-requests`です。
すべてFirebaseの`Authorization: Bearer <IDトークン>`が必須です。
既存の`get_project_team_member`と`get_accessible_project`を再利用し、
ProjectとTeamの対応を確認します。レビュー依頼番号だけを知っても他のProjectからは取得できません。

### POST 共通パス：提出

```json
{
  "request_key": "b10f1659-59e7-4c37-886a-9410b68ce5a3",
  "title": "ログイン画面の説明文を修正",
  "description": "操作が分かりやすくなるように変更しました。"
}
```

タイトルは前後の空白除去後に1〜200文字で検証します。説明はnull・省略が可能です。
不正なUnicode、NUL等の制御文字、型や長さが不正な入力は422です。
ユーザーID・パス・Gitコマンド等の余計なフィールドも422で拒否します。

初回はHTTP 201、同じ提出キー・同じタイトルと説明の再試行はHTTP 200と既存の依頼を返します。
同じキーで別の説明等を送ると409です。再試行時に作業ファイルが変わっていても、
すでに固定された提出があればそのスナップショットを再利用します。
新たな変更を提出する場合だけ新しいUUIDを使ってください。

共有mainとのファイル・実行属性の差がなければ409（No changes to submit）です。
まだmainにコミットがない場合は空の内容と比較します。
比較元は専用の空コミットとして保持し、共有mainやHEADは更新しません。

### GET 共通パス：一覧

`limit`（1〜100、既定50）と`offset`（0以上、既定0）を指定できます。
作成日時・IDの降順で、対象プロジェクトだけを返します。未提出なら空配列です。

### GET 共通パス/{id}：詳細

提出者ID・名前、タイトル・説明・状態、提出日時、基準・提出コミットID、Git参照を返します。
個人の作業領域の現在の内容は読み取りません。

### GET 共通パス/{id}/diff：変更ファイルと差分

基準コミットと提出コミットを比較し、ファイルごとに次を返します。

| 項目 | 内容 |
| --- | --- |
| path | 検証済みのUTF-8相対パス |
| change | A（追加）/ M（変更）/ D（削除） |
| binary | NUL等の制御文字や非UTF-8を含み、テキスト差分を出さない場合true |
| mode_changed | 実行属性の変更がある場合true |
| patch | unified diff形式の文字列。バイナリや制限超過時はnull |
| truncated | テキスト差分の制限を超えて省略した場合true |

レスポンス全体にもtruncatedを返します。ファイル名の変更は「削除＋追加」で表示します。
バイナリ自体は保存しますが内容をJSONへ展開しません。差分をHTMLとして実行・表示しないでください。
将来のVue画面ではテキストとしてエスケープ表示する必要があります。

## ファイルの固定方法と安全性

利用者の`.git/config`、index、HEAD、hooks、remoteをGitで開かないことが重要です。
`.git`は初期化時の本人確認マーカーだけを読み取り、提出ファイルには含めません。

1. 既存ProjectStorageのディレクトリFD・O_NOFOLLOW・プロジェクトロックを再利用する。
2. 認証済みUserの領域だけを再帰的に読み取る。symlink、ハードリンク、FIFO等は拒否する。
3. ファイルのinode・サイズ・mtime・ctime・モードを読み取り前後で照合し、全体も二回読み取って比較する。
   途中の変更を検出したら409で止める。収集後の編集は提出スナップショットに影響しない。
4. サーバーが新しく作った一時bareリポジトリの設定だけでhash-object／mktree／commit-treeを実行する。
   raw bytesをstdinで渡し、属性フィルターや作業領域のGitフックは実行しない。
5. オブジェクトは既存の共有bareのobjectsへ保存する。共有側のconfigも実行時設定として読み込まない。
   外部オブジェクトストアを指定するalternates／http-alternatesがあれば拒否する。
6. Gitオブジェクト・復旧記録・専用参照を永続化してからDBへ登録する。

Gitは引数配列・shell=False、最小限の環境変数、外部プロトコル禁止、フック禁止、
自動GC禁止で実行します。利用者が指定するGit操作のAPIはありません。
Gitの生の標準エラー、内部絶対パス、SQLエラーをレスポンスへ出しません。
共有main、個人のindex・HEAD・ファイル内容は変更しません。

第1段階と同じSHA-1形式のリポジトリを対象にしています。SHA-256形式への移行は別途必要です。
保存ルートと共有bare・復旧記録はバックエンド専用で、利用者コンテナへ公開しない前提です。
Dockerソケットのアクセスは追加していません。

### 提出範囲と上限

提出は作業領域全体の通常ファイルです。未追跡ファイルも含み、`.gitignore`のパターンは評価しません。
利用者のGit設定を読み込まずに対象を確定するための仕様です。
秘密情報や提出したくない生成物をこの領域へ配置しないでください。
APIがサーバー側の秘密鍵や任意のホストパスを読み取る機能はありません。

| 項目 | 上限 |
| --- | --- |
| ファイル数 | 1,000 |
| ディレクトリを含む検査エントリー数 | 2,000 |
| ファイル単体 | 1 MiB |
| ファイル内容の合計 | 10 MiB |
| パスの深さ / UTF-8バイト数 | 20階層 / 512 bytes |
| テキスト差分の合計 | 256 KiB |
| 1ファイルの差分計算対象 | 元と変更後の合計256 KiB・4,000改行以下 |
| Git子プロセス | 1回につき最大30秒 |

処理の区切りで全体60秒の期限も確認し、超過した場合は503とします。
ファイル・履歴・Git出力が上限を超える場合は413です。
テキスト差分だけが上限を超える場合は200とtruncated=trueで、ファイル一覧は残します。
不正なパス・ネストした.git・特殊ファイル・Git履歴のsymlink／submoduleは拒否します。
小さいパッチを生成して適用する機能ではなく、レビュー用の表示データを返すAPIです。

## 不変のGit参照とDBとの復旧

サーバーが(Project, User, request_key)から生成したキーを使い、以下を保持します。

```text
projects/<project_id>/
  shared.git/refs/change-requests/<key>/base
  shared.git/refs/change-requests/<key>/head
  review-journal/<key>.json
```

baseとheadの参照がGitの到達可能性を維持するため、DBにIDだけを保存する場合と違い、
通常のGit GCで提出オブジェクトが消えることを防ぎます。packed-refs化された参照も読み取れます。
既存の参照が違うIDを指す場合は、自動で上書き・削除せず409で停止します。

DBとGitを一つのトランザクションにはできません。プロジェクトロックの中で、
スナップショット作成→復旧用JSON→base/head参照→DBコミットの順に実行します。
Gitのfsync設定と、記録・参照・親ディレクトリのfsyncを使用します。
正式ファイルは一度だけ作成し、既存ファイルを上書きしない原子的renameで公開します。

| 失敗・不一致 | 扱いと復旧 |
| --- | --- |
| 復旧用JSONを保存する前に失敗 | DBには登録しない。再試行では現在の作業ファイルを改めて収集する。まだ提出は確定していない |
| JSON保存後、参照作成に失敗 | 同じキーと入力で再試行し、JSONに記録した同じコミットの参照を作成する |
| 参照保存後、DBが失敗 | DBだけロールバック。Gitを消さず、同じキーと入力で同じスナップショットをDBへ登録する |
| DB成功後、応答が失敗 | 同じキーで再試行すると200と既存の依頼を返す |
| DBはあるがJSONが欠けた | 同じ提出の再試行でDBからJSONを復元。コミットの存在を確認して参照も照合する |
| JSON・DBと既存参照の値が違う | 409で止める。管理者がバックアップ・記録を確認する。上書きしない |
| 参照だけ欠けた | diffは503。同じ提出を再試行すれば、オブジェクトが残っている場合にだけ復元する |
| Gitオブジェクトも失われた | 復旧を完了しない。DBと保存ボリュームの対応するバックアップから管理者が復元する |

同じキーの同時提出は既存のファイルロックとDBの一意制約により一件にまとめます。
別ユーザーには別のキー空間と作業領域を使います。異なる提出キーなら同内容でも別の依頼として扱います。
今後のmain更新・保守・GCも同じプロジェクトロックで直列化する必要があります。

**未登録の復旧用JSONがある状態で手動pruneしないでください。**
JSON保存直後に失敗するとbase/head参照がまだ揃っていない可能性があります。
先に同じキーの再試行で参照とDBを復旧してください。自動GCや削除機能は今回追加していません。
バックアップはDBとproject_storageの両方を保存し、作業領域・復旧用JSON・Git参照を保全します。
未完了の.pendingファイルや未参照オブジェクトは自動削除しません。

この段階では単一Linuxホスト・ローカル永続ボリュームが対象です。
別ホストの別ボリュームで同一Projectを同時処理する構成は対象外です。
外部で実行したGit操作やファイルの削除まで防ぐ仕組みではありません。

## PostgreSQLへの反映

`backend/migrations/002_change_requests.sql`は新テーブルとインデックスの追加だけです。
既存のProject、User、Teamやそのデータは変更しません。
同名テーブルがある場合は列構成と必要な制約を確認し、不一致なら中止します。
不足した制約を勝手に補正したり、データを消して再作成したりしません。

バックアップを確保し、対象DBを確認したうえで、次の形で手動適用してください。

```text
psql -v ON_ERROR_STOP=1 -f backend/migrations/002_change_requests.sql
```

DB接続情報は環境変数等で設定し、コマンドやGitへ秘密情報を保存しないでください。
トランザクションで実行し、失敗時はロールバックします。再実行もテストしています。
既存の起動時create_allは新規DBではテーブルを追加しますが、既存構造の補正はしません。
稼働中DBには今回の作業から移行SQLを適用していません。

## WindowsとLinuxでのテスト

一覧・詳細のメタデータ取得はWindowsでも動作します。
スナップショット作成・Git差分は既存ProjectStorageと同じLinux専用で、Windows直接起動時は503です。
安全性を落とすWindows用の代替パス操作は追加していません。

backendで`python -m unittest discover -s tests -v`を実行します。
実Gitを使うテストはDocker内Linuxで実行してください。

```text
docker build -t progress-change-request-test backend
docker run --rm progress-change-request-test python -m unittest discover -s tests -v
```

`PROJECT_TEST_DATABASE_URL`を一時PostgreSQLへ指定すれば、専用スキーマでDBと移行テストを実行できます。
テストは新規の一時作業領域とDBスキーマだけを使い、既存の保存ボリュームやFirebase秘密鍵を読み込みません。
Firebaseの外部トークン検証だけを代替し、APIの認証ヘッダー・所属・Project判定は実際の処理を通します。

実Firebase通信、実ブラウザ、実機の電源断、複数ホスト、任意コード実行者が動作中の本番エディタは未検証です。
第2段階の本番エディタは未実装のままです。これらを自動テスト成功と混同しないでください。
