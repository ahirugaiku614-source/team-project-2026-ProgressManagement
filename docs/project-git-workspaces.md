# 共有Gitと個人作業領域：第1段階

## 今回できること

最新mainの`c09291f`を基準に、既存ProjectのIDに対応する共有Gitリポジトリと、
認証済みユーザーごとの作業領域を準備します。利用者のGitHubアカウントは不要です。
既存Projectのカラム・データ、タスク・個人コードファイルAPIは変更しません。

今回は準備と状態確認だけを提供します。共有リポジトリも個人のリポジトリも
初期状態はコミットのない`main`ブランチです。ワークスペースは共有コードの複製や同期をまだ行いません。
レビュー提出・承認・差し戻し、共有コードへの統合、最新版取得、競合解決、エディタ画面は未実装です。
空のリポジトリではHEADが`main`を指していても、最初のコミットまでブランチの参照は存在しません。

## 保存場所とアクセス境界

backendだけに新しい名前付きDockerボリューム`project_storage`をマウントします。
コンテナ内の保存ルートは`PROJECT_STORAGE_ROOT=/var/lib/team-projects`です。

```text
/var/lib/team-projects/
  projects/
    <project_id>/
      .init.lock
      shared.git/              # 共有用bareリポジトリ（作業ファイルを持たない）
      workspaces/
        <user_id>/             # 個人の作業ファイル領域
          .git/                # 個人の独立したGit管理領域
```

プロジェクトIDはDBで一意なので、チームIDをパスに重ねなくてもプロジェクト間で分離できます。
パスにはプロジェクト名、メール、リクエストのファイル名を使用しません。
共有リポジトリとワークスペースのGit管理領域に、プロジェクトID・ユーザーID・形式バージョンを
含む内部マーカー`.storage-ready.json`を保持します。個人側は`.git`内なので通常のコードには含まれません。

frontendと現在のcode-serverにはこのボリュームをマウントしません。
既存の共通パスワードcode-serverはローカル検証用のままです。今回の認可の代用にはしていません。
バックエンド専用保存領域は、他のコンテナや利用者が任意に書き換えられないことが前提です。
アプリのAPI認可とパス分離は、任意コード実行環境のOS隔離を代替しません。

将来はユーザー別コンテナに、そのユーザー・プロジェクトの作業領域だけを渡します。
共有bareリポジトリ・他人の領域・Dockerソケットは渡しません。
現時点の`origin`はバックエンド内の共有リポジトリのパスを記録するだけです。
利用者の環境へ共有領域をマウントして自由にpushさせる設計にはしません。
将来の共有コード更新は、承認を検証するバックエンド操作だけに限定する必要があります。

## API

共通URLは`/api/teams/{team_id}/projects/{project_id}`です。
Firebaseの`Authorization: Bearer <IDトークン>`を必須とし、既存の
`get_project_team_member`でユーザー・チーム・所属を確認した後、
指定Projectが指定チームのものかをDBで照合します。
`user_id`は認証済みUserから取得し、リクエスト中のユーザーIDは使用しません。

| メソッド・末尾パス | 処理 |
| --- | --- |
| POST `/repository/init` | 共有リポジトリを初期化。初期化済みなら保持 |
| GET `/repository` | 共有リポジトリの状態確認。ファイルを作成しない |
| POST `/workspace/init` | 共有リポジトリと自分の作業領域を初期化。初期化済みなら保持 |
| GET `/workspace` | 共有リポジトリと自分の作業領域の状態確認。ファイルを作成しない |

いずれも成功時はHTTP 200です。初回と再実行で同じ形式を返します。

```json
{
  "project_id": 1,
  "repository_state": "ready",
  "default_branch": "main",
  "user_id": 2,
  "workspace_state": "ready"
}
```

`user_id`と`workspace_state`はworkspace APIだけが返します。
内部パス、Gitの標準エラー出力、秘密情報は返しません。

状態の意味は`missing`（未作成）、`ready`（初期化完了マーカーと必要な構造あり）、
`incomplete`（領域は存在するが形式・完了条件が不一致）です。
`ready`はGit全オブジェクトの整合性検査や最新版への同期完了を意味しません。

認証失敗は既存の401／403、所属外は403、存在しないProjectや別チームのProjectは404です。
不完全な既存領域への初期化やシンボリックリンク等の危険な構造は409、
Gitの失敗・タイムアウト・保存先のアクセス不可・ロック待機超過は503です。
Linux以外で新APIを使った場合も、安全性を落とす代替処理はせず503にします。
既存APIはWindows上でも従来どおり利用・テストできます。

## 初期化と途中失敗

1. 既存のプロジェクト作成APIでDBにProjectを保存します。ここではファイルを作成しません。
2. 保存成功後、必要なタイミングで初期化APIを呼びます。過去に作成したProjectにも利用できます。
3. プロジェクト単位のファイルロックを取得し、既存領域の状態を確認します。
4. 同じ親ディレクトリに一意の`.staging-<UUID>`を作り、そこでGitを初期化します。
5. Gitのファイルとディレクトリをfsyncし、完了マーカーを保存します。
6. Linuxの`renameat2(RENAME_NOREPLACE)`で完成した領域だけを公開し、親もfsyncします。

DBとファイルシステムを一つのトランザクションにすることはできないため、
DBのProjectを操作の前提とし、初期化状態は実際の保存領域から判断します。
DBに初期化済みフラグやパスは保存せず、二重管理による食い違いを避けます。
既存Project作成APIがDB保存に失敗した場合、領域は作られません。
初期化APIはDBデータを書き換えません。

| 失敗した地点 | 残る状態と再実行 |
| --- | --- |
| Git初期化・マーカー保存・公開前 | 未公開のstagingを保持。新しいstagingで再実行可能 |
| 共有リポジトリ成功後、個人領域の処理失敗 | 共有リポジトリを保持。再実行では個人領域だけ作成 |
| 公開成功後に応答が失敗 | 再実行は既存領域を検証して返す。再初期化しない |
| 正式パスに不完全な領域・不一致のマーカーがある | 409で停止。自動修復・上書き・削除はしない |
| ロック待機が10秒を超える | 503。後で再実行 |

同じプロジェクトの初期化は別スレッド・別プロセスでも`flock`で直列化します。
待機プロセスはロック解放後に状態を再確認します。
予期せず公開先ができても、原子的な上書き禁止renameでデータを保持します。
状態確認はロック不要で、公開前はmissing、公開後はreadyを返します。

stagingは失敗調査用に残し、この段階では自動削除しません。
ディスク容量監視、運用者による回収手順、レート制限・容量上限は今後の課題です。
異常な既存領域も調査・バックアップ・方針確認前に削除しないでください。
ファイルロック・原子的rename・fsyncをサポートするローカルLinuxボリュームを使います。
複数ホスト間の共有ストレージやNFSでの運用、電源断時の実機試験は未検証です。

## パスとGitコマンドの安全性

- DBから認可された正の整数IDだけでパスを作ります。文字列IDや`..`を拒否します。
- ルートの全階層からディレクトリFDと`O_NOFOLLOW`を使い、シンボリックリンクを辿りません。
  ロック・完了マーカー・Git管理ファイルにも同様の検査を適用します。
- 領域内のシンボリックリンク、複数リンクを持つファイル、FIFOなどの特殊ファイルを拒否します。
  ローカルcloneのハードリンク共有も前提にしていません。
- Gitは引数配列と`shell=False`で実行します。外部入力をコマンドとして連結しません。
  対象ディレクトリは開いたFDに固定し、コマンドごとに30秒の制限を設けます。
- Git環境変数を引き継がず、システム・ユーザーの設定、テンプレート、フックの混入を防ぎます。
  初期化済み領域に対してGitコマンドを再実行しません。

将来、利用者が任意のファイルを作れるようにする際は、安全なファイルAPIやコンテナ境界を設計し、
Git設定・フック・symlinkを含む入力を信頼しない処理を追加してください。
今回の状態確認はファイルツリーを走査するため、大規模領域の性能評価も必要です。

## Dockerと反映手順

backendのDockerfileにGitを追加しました。`.dockerignore`でFirebase秘密鍵・envファイルを除外します。
Composeは従来どおりホストのbackendディレクトリをマウントするため、秘密鍵の既存設定は維持します。
イメージ単体で本番起動する際は、秘密鍵を別途安全にマウントする必要があります。

バックアップ確認後、ルートで`docker compose up -d --build backend`を実行してください。
既存DBのマイグレーションや既存ボリュームの作り直しは不要です。
初期化は自動で全Projectに実行せず、必要なProjectにAPIで要求します。
保存先変更による既存領域の移動や削除も自動では行いません。

## テストの再実行

LinuxとGitのある環境で、backendから次を実行します。

```text
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
```

Dockerでも検証できます（テスト用コンテナは既存ボリュームをマウントしません）。

```text
docker build -t project-storage-tests backend
docker run --rm project-storage-tests python -m unittest discover -s tests -v
```

`PROJECT_TEST_DATABASE_URL`を一時PostgreSQLに設定すれば、既存のランダム専用スキーマで
API・DB回帰・既存移行SQLのテストも実行できます。実`.env`・Firebase秘密鍵は不要です。
コンテナ内にDocker CLIがなければCompose設定テストはスキップされるので、ホスト側で別途実行します。

## 次の段階

レビュー提出データと差分、別メンバーによる承認、承認時だけの共有リポジトリ更新、
作業内容を失わない最新版取得を追加します。Git操作はバックエンドで実施します。
ユーザー別code-serverの認証・通信経路・プロセス隔離も別の実装段階です。
Project削除、チーム脱退、退会後の領域保持方針は設計が必要で、今回は削除処理を追加していません。
